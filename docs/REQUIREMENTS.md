# AgentFlow 产品需求文档（PRD）

> 产品定位：Android 上可观察、可授权、可恢复的 AI Agent 工作空间  
> 当前核心场景：在 Android 设备上完成可审查、可验证的代码项目任务  
> 文档状态：Draft 1.0  
> 更新日期：2026-09-28

## 1. 产品摘要

AgentFlow 不是在 Android 平板上增加一个 AI 聊天框，而是让用户把一个完整任务交给 Agent，并在统一工作空间中查看计划、授权操作、审查变更和验证结果。

长期愿景是构建 **AI-native personal computer**；当前阶段不重新开发操作系统，而是先验证一个明确价值：

> 用户能将一个代码项目交给 Android 设备上的 AgentFlow，要求它分析或修改项目；Agent 在受限范围内执行任务，并交付可审查、可撤销、带验证证据的结果。

产品核心链路：

```text
用户目标 → 任务计划 → 权限判断 → 工具执行 → 过程记录 → 变更审查 → 结果验证 → 任务报告
```

## 2. 背景与问题

现有移动端 AI 产品大多以“提问—回答”为核心，不能稳定完成跨文件、跨工具、需要持续执行和验证的任务：

- 用户不知道 Agent 当前正在做什么，也无法判断是否卡住。
- 授权没有与具体任务、目录和操作绑定。
- 代码修改缺少 Diff、测试结果及其他可验证证据。
- 长任务退出页面或应用重启后难以恢复。
- 文件、终端、日志和最终产物分散，缺少统一任务工作区。
- Android 缺少直接面向开发任务的 Shell、Git、Node.js、Python 等统一运行环境。

AgentFlow 要解决的不是“怎样让 AI 回答得更多”，而是：

> 怎样让 AI 在 Android 上可靠、安全、透明地完成一个真实任务。

## 3. 产品目标

### 3.1 当前目标

1. 打通从导入项目到分析、修改、测试、报告的完整任务链路。
2. 让用户能够理解 Agent 的计划、当前状态、工具动作和执行结果。
3. 将权限约束到当前任务、指定工作区、具体工具和有效期限。
4. 所有代码修改均可预览、拒绝、接受和撤销。
5. 所有“任务已完成”结论均附带验证状态和证据。
6. 支持本地或远程 Runtime，避免 Agent Core 与某种运行环境绑定。

### 3.2 长期目标

- 从 Coding Agent 扩展到文档、浏览器、知识和 Android 系统任务。
- 形成由 Workspace、Task、Tools、Runtime、Memory 和 Permission 组成的 AI Operating Workspace。
- 支持触摸、键鼠、文字、语音和视觉等多模态交互。

### 3.3 非目标

当前版本不以以下事项为目标：

- 替代 Android 系统或开发自有 ROM。
- 复制完整的 VS Code、Office 或桌面窗口系统。
- 无监督执行删除、支付、登录、推送代码等高风险动作。
- 通过纯视觉坐标控制任意 Android 应用。
- 构建复杂知识图谱、插件市场、多 Agent 协作或本地大模型平台。
- 保证任意技术栈的项目都能在 Android 本机编译运行。

## 4. 目标用户与核心场景

### 4.1 目标用户

首批用户是熟悉代码和 Git、愿意审查 Agent 行为的开发者：

- 使用 Android 平板进行轻量开发、排障或远程运维的开发者。
- 离开桌面电脑时，需要查看、分析或小幅修改项目的开发者。
- 希望将重复分析、搜索、修改和测试步骤交给 Agent 的高级用户。

当前版本不面向完全不了解文件、命令和代码变更风险的普通消费者。

### 4.2 核心用户任务（JTBD）

当我只有 Android 设备时，我希望把一个代码项目和清晰目标交给 Agent，让它在我授权的范围内完成分析或修改，并提供足够证据供我审查，从而无需手工切换文件管理器、终端、编辑器和聊天应用。

### 4.3 首个端到端场景

```text
创建 Workspace
  → 选择本地项目或连接远程项目
  → 输入“分析并修复这个问题”
  → Agent 检查项目并提出计划
  → 用户确认任务范围
  → Agent 搜索、读取和分析代码
  → Agent 请求修改或执行命令的权限
  → 用户查看并批准
  → Agent 应用补丁并运行测试
  → 用户审查 Diff、日志和测试结果
  → Agent 输出结论、风险和未完成事项
```

## 5. 产品原则

### 5.1 任务优先，聊天是入口

每次需要执行环境操作的用户请求都应形成 Task。聊天负责表达意图和补充信息，不承载完整执行状态。

### 5.2 结构化能力优先

能力选择优先级：

```text
结构化 Tool/API → Android Intent → Accessibility/UI Tree → Vision → 屏幕坐标
```

当前 Coding MVP 只要求结构化 Tool，不依赖视觉操作。

### 5.3 默认最小权限

权限必须同时描述任务、能力、资源范围、风险等级和有效期。不得仅以“Agent 已获文件权限”代表无限制访问。

### 5.4 变更可审查、可撤销

Agent 不得静默覆盖用户文件。所有写入必须保留基线、展示 Diff，并能够拒绝或撤销。

### 5.5 完成必须可验证

Agent 必须区分：已执行且验证通过、已执行但验证失败、已修改但未验证、仅提出建议但未执行。

### 5.6 失败可恢复

任务、步骤、工具调用、审批和产物需要持久化。应用重启后应能查看历史状态，并在安全条件满足时继续任务。

## 6. 核心产品对象

| 对象 | 定义 | 关键内容 |
| --- | --- | --- |
| Workspace | 用户授权给 Agent 的工作边界 | 项目、Runtime、根目录、配置、任务和产物 |
| Task | 一次有明确目标和生命周期的工作 | 目标、计划、状态、权限、步骤、结果 |
| Step | Task 中可跟踪的执行单元 | 状态、工具调用、输入摘要、输出摘要、错误 |
| Capability | Agent 可申请使用的能力 | 文件读取、文件修改、Shell、Git、网络等 |
| Approval | 用户对特定风险动作的授权决定 | 范围、有效期、允许或拒绝、时间 |
| Change Set | 一组待审查的文件变更 | 基线、Diff、接受状态、回滚信息 |
| Evidence | 支撑任务结论的证据 | 命令、日志、退出码、测试结果、文件引用 |
| Artifact | Task 产生的可交付结果 | 报告、补丁、日志、导出文件 |
| Runtime | 实际执行文件和命令操作的环境 | Local、Android/Termux、SSH |

## 7. MVP 功能需求

### PRD-WS-01 创建和管理 Workspace（P0）

用户可以创建、重命名、切换和归档 Workspace，选择项目根目录和 Runtime，并查看 Runtime 状态、历史 Task 和产物。

验收标准：

- 应用重启后 Workspace、根目录和 Runtime 绑定仍然存在。
- 所有文件工具均不能访问 Workspace 根目录以外的路径。
- Runtime 不可用时，界面明确说明原因和受影响能力。

### PRD-TASK-01 创建任务（P0）

用户输入目标后，系统创建 Task，而不是只生成一条聊天回复。Task 至少包含标题、原始目标、状态、计划、步骤、时间、权限、Change Set、Evidence 和最终报告。

验收标准：

- 用户可从 Workspace 找回任一历史 Task。
- 同一时刻每个 Workspace 默认只运行一个写任务。
- 缺少项目、模型或 Runtime 时，不得进入执行状态，并显示修复入口。

### PRD-TASK-02 计划确认（P0）

当任务可能修改文件、执行命令或访问网络时，Agent 在首次高风险操作前展示：目标理解、主要步骤、预计使用的能力、已知风险和待确认信息。用户可以开始、补充要求或取消。

对于纯只读、低风险分析任务，用户可配置跳过计划确认。

### PRD-ACT-01 活动时间线（P0）

系统展示 Agent 的外部行为，而不是模型内部思维。每项活动显示动作名称、状态、工具、目标资源、开始时间、输出摘要、耗时和可展开详情。

验收标准：

- 用户能够判断 Agent 当前步骤及是否仍在运行。
- 工具失败时显示可理解的错误及重试入口。
- 日志中的令牌、密码、私钥和敏感 Header 必须被清理。

### PRD-TOOL-01 文件与代码工具（P0）

MVP 提供目录列表、文本读取、文件与代码搜索、创建或应用补丁、文件变化检查、Git 状态和 Diff。

约束：

- 默认禁止路径逃逸和符号链接越界。
- 二进制文件和超大文本文件不得直接完整送入模型。
- 写入前检查基线版本，避免覆盖用户或其他进程的新修改。

### PRD-TOOL-02 Shell 与进程工具（P0）

MVP 支持在 Workspace 工作目录中执行一次性命令，获取 stdout、stderr、退出码、耗时和超时状态，取消命令并展示终端日志。

验收标准：

- 命令卡片明确展示 Runtime 和工作目录。
- 超时、取消和非零退出码不得标记为成功。
- Agent 不能通过命令拼接绕过工作区和审批策略。

### PRD-TOOL-03 Git 工具（P0）

MVP 支持只读的 status、diff 和日志摘要。Commit 属于 P1；Push 不进入 MVP。

验收标准：

- 用户可以区分任务开始前已有变更和 Agent 新增变更。
- Agent 不得覆盖、清理或提交用户已有的未提交变更。

### PRD-DIFF-01 变更审查（P0）

Agent 写入文件后生成 Change Set。用户可以按文件查看 Diff，接受或拒绝单个/全部变更，查看冲突，并在任务结束前撤销 Agent 已应用的变更。

验收标准：

- 未经授权不得持久化写入。
- Diff 必须基于任务开始时或写入前确认的基线。
- 拒绝或撤销不得破坏任务前已有内容。

### PRD-PERM-01 权限与审批（P0）

| 能力 | 默认风险 | 默认策略 |
| --- | --- | --- |
| 工作区内读取与搜索 | 低 | 自动允许 |
| Git 状态与 Diff | 低 | 自动允许 |
| 工作区内写入 | 中 | 首次确认或逐变更确认 |
| Shell 命令 | 中/高 | 按命令确认 |
| 网络访问或安装依赖 | 高 | 明确确认 |
| Git Commit | 高 | 强确认 |
| Git Push、删除、访问工作区外文件 | 极高 | MVP 禁止 |

审批卡必须展示动作、能力、目标资源、风险和可能影响，并提供“允许一次”“本任务允许”和“拒绝”。只有安全能力可以提供更长期授权；审批范围变化时必须重新请求。

### PRD-VERIFY-01 验证与证据（P0）

Agent 完成修改后应执行相关验证，例如测试、构建、静态检查或用户指定命令。最终报告必须包含：

- 完成了什么及修改了哪些文件。
- 执行了哪些验证及关键证据。
- 未验证内容、失败项和剩余风险。

如果无法验证，状态必须是“已完成但未验证”或“部分完成”，不能声称任务成功。

### PRD-RECOVER-01 中断和恢复（P0）

用户可以取消正在执行的步骤或整个 Task。应用异常退出或被系统回收后：

- 已完成活动和产物不得丢失。
- 未完成进程标记为“状态未知”或“已中断”。
- 恢复前重新检查 Workspace、Runtime、文件基线和权限。
- 不得在用户不知情时自动重放写入或高风险命令。

## 8. 后续范围

### P1：MVP 稳定后

- 轻量代码编辑器，作为 Agent 结果的人工接管界面。
- SSH Remote Runtime 和远程文件访问。
- 流式长进程终端。
- HTTP/stdio MCP 工具接入。
- Git Commit 审批流程。
- PDF/EPUB 导入、搜索、引用和问答。
- 项目级任务摘要和受控记忆。

### P2：验证需求后

- 浏览器语义工具和 Computer Use。
- Android Intent、Accessibility 和 UI Tree 工具。
- 语音输入与任务播报。
- 摄像头、OCR 和视觉上下文。
- 本地模型和模型路由。
- 通用个人知识系统。

## 9. Agent 生命周期

```text
DRAFT
  → PLANNING
  → WAITING_CONFIRMATION
  → RUNNING
      ↔ WAITING_APPROVAL
      ↔ WAITING_USER_INPUT
  → VERIFYING
  → COMPLETED | PARTIAL | FAILED | CANCELLED
```

规则：

- 状态改变必须写入持久化记录。
- `WAITING_APPROVAL` 必须指向一个未决审批。
- `COMPLETED` 必须存在最终报告；执行型任务还必须存在验证记录。
- 模型停止输出不等于任务完成。
- 工具失败后可在原权限范围内重试；扩大作用域或提高风险必须重新审批。

## 10. 关键交互要求

### 10.1 Workspace 首页

首页优先展示当前 Workspace 和 Runtime 状态、继续上次 Task、新任务输入框、最近 Task，以及待处理审批、变更或失败。不以应用图标网格或空白聊天记录作为主界面。

### 10.2 Task 页面

Task 页面由四部分组成：目标与计划、实时活动时间线、审批与 Change Set、最终报告与验证证据。用户无需进入终端即可理解任务总体进度。

### 10.3 终端与日志

终端属于证据和排障界面，不作为唯一状态来源。默认显示摘要，用户可展开完整输出、复制日志或跳转错误位置。

### 10.4 通知

应用位于后台时，仅在需要审批或补充输入、长任务完成或失败、Runtime 意外断开时通知。通知不得包含密钥、完整命令输出或敏感文件内容。

## 11. Runtime 与工具边界

Agent Core 只依赖统一 Runtime 和 Tool 接口，不直接依赖 Termux、SSH 或具体 Android 实现。

```text
UI → Agent Engine → Capability / Approval → Tool Registry → Runtime → Local / Android Bridge / SSH
```

每次工具调用至少记录：

```text
toolCallId, taskId, capability, runtimeId, resourceScope, riskLevel,
approvalId, startedAt, finishedAt, resultStatus, outputSummary, evidenceReference
```

工具输出必须限制大小；完整内容作为本地产物保存，只向模型提供必要摘要或片段。

## 12. 数据与记忆

### 12.1 本地优先

Workspace、Task、Activity、Approval、Change Set 和 Evidence 默认保存在本地数据库或工作区产物目录中。模型密钥、SSH 密码、私钥口令等必须进入安全存储，不得进入 SQLite、日志、模型上下文或任务报告。

### 12.2 记忆边界

MVP 只保留完成任务所需的项目上下文和任务摘要，不自动建立跨 Workspace 的个人长期记忆。记忆必须来源明确、具有稳定价值、可由用户查看和删除，且不包含密钥或无关个人数据。

## 13. 非功能需求

### 13.1 安全

- 所有路径在执行前规范化并验证处于授权根目录内。
- 外部工具返回的文字视为不可信数据，不能自行扩大权限。
- 高风险审批不可由模型生成的文字自动替代。
- 任务导出默认清理密钥、Cookie、Authorization Header 和个人路径信息。
- 远程 Runtime 首次连接必须确认 Host Key，变化时阻止连接。

### 13.2 可靠性

- 工具调用、审批和状态迁移采用稳定 ID，避免重复执行。
- 写文件优先使用临时文件加原子替换；失败时保留原文件。
- 进程执行支持超时和取消。
- 数据库升级不得丢失已有 Workspace 和 Task。

### 13.3 性能

- Workspace 首页在普通本地数据量下应在 2 秒内可交互。
- Agent 活动事件产生后 500 ms 内更新界面。
- 大型目录、搜索结果和日志采用分页、裁剪或流式展示。
- 不将完整仓库或完整历史记录一次性发送给模型。

### 13.4 可用性

- 关键状态不能只依赖颜色表达。
- 审批卡和错误信息使用用户可理解的动作语言。
- 平板横屏为主要布局，同时保证手机竖屏可完成核心任务。
- 键盘和触摸均可完成任务创建、审批、Diff 审查和取消操作。

## 14. 成功指标

### 14.1 北极星指标

**可验证任务完成率**：进入执行状态的 Task 中，最终达到 `COMPLETED`，且存在用户可查看验证证据的比例。

### 14.2 产品指标

- 首次成功：新用户创建 Workspace 后完成首个可验证 Task 的比例。
- 端到端成功率：无需离开 AgentFlow 即完成分析、变更和验证的任务比例。
- 审批清晰度：审批后立即撤销或报告“未理解影响”的比例。
- 恢复成功率：中断后能够安全恢复或明确结束的任务比例。
- 变更接受率：Agent Change Set 被用户全部或部分接受的比例。
- 错误透明度：工具失败后展示具体原因和可操作建议的覆盖率。

不以对话次数、消息长度或模型调用次数作为核心成功指标。

## 15. 里程碑与发布门槛

### Milestone A：可观察的只读 Agent

- Workspace 与 Runtime 绑定。
- Task、计划和活动时间线。
- 文件读取、目录列表、代码搜索、Git 状态。
- 只读项目分析报告。

发布门槛：Agent 能分析一个真实项目，所有引用可回溯到文件和工具结果。

### Milestone B：可授权的修改 Agent

- 能力与审批系统。
- 补丁写入、基线冲突检查和 Diff 审查。
- Shell 执行、超时、取消和日志。
- 测试或构建验证。

发布门槛：Agent 能完成一次“分析—修改—测试—报告”，且不会覆盖任务前已有修改。

### Milestone C：可恢复的工作空间

- Task、Activity、Approval、Evidence 持久化。
- 后台执行状态与必要通知。
- 异常中断检测和安全恢复。
- 完整任务报告和产物导出。

发布门槛：应用重启后能够准确还原 Task，且不会自动重复高风险动作。

### Milestone D：扩展运行环境

- SSH Runtime、长进程和流式终端。
- MCP 工具接入。
- 轻量编辑器人工接管。

实现拆分见 [MVP3_MVP4_DEVELOPMENT_PLAN.md](./MVP3_MVP4_DEVELOPMENT_PLAN.md) 和 [CODE_EDITOR_PLAN.md](./CODE_EDITOR_PLAN.md)。

## 16. MVP 发布验收场景

版本发布前必须通过以下端到端场景：

1. 用户创建 Workspace 并导入一个包含未提交修改的 Git 项目。
2. 用户要求 Agent 定位并修复一个具备自动化测试的问题。
3. Agent 展示计划，读取和搜索代码，并明确区分已有修改。
4. Agent 在首次写入和执行命令前申请正确权限。
5. 用户批准后，Agent 生成可审查 Diff，并且不覆盖已有修改。
6. Agent 运行测试，记录命令、退出码和关键输出。
7. Agent 输出包含变更文件、验证结果、未完成项和风险的报告。
8. 用户能够撤销 Agent 的变更，项目恢复到任务开始前且保留原有修改。
9. 在安全节点重启应用，Task 记录均可恢复，且高风险动作不会被重复执行。

## 17. 后续决策点

以下问题应通过 MVP 使用数据和用户访谈决定：

- 本地 Android/Termux 与 SSH，哪一种 Runtime 是主要使用方式？
- 用户更需要自主修改，还是只读分析与建议？
- 审批应以每条命令、每类能力还是每个任务为主要粒度？
- 轻量编辑器是否足以人工接管，还是需要与外部编辑器协作？
- 文档 Agent、浏览器 Agent 和 Android Computer Use 中，哪一个是第二条高频链路？

## 18. 产品定位表述

对外愿景：

> **AgentFlow — AI-native personal computer.**

当前产品描述：

> **AgentFlow 是运行在 Android 上的 AI Agent 工作空间。用户交付目标，Agent 在受控工作区中分析项目、修改代码、运行验证，并提供可审查的过程与结果。**

第一阶段价值主张：

> **把项目交给 AgentFlow，回来审查一份已经验证过的修改。**
